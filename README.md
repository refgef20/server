# Бэкенд админ-панели

Админ-панель работает с существующими моделями Sequelize, проверкой JWT в `authorization.js` и проверкой прав в `roleMiddleware.js`.

## Управление аккаунтами

В `controllers/adminController.js` добавлены три функции. Они подключены через `routes/adminRouter.js` по префиксу `/api/admin` в `server.js`.

| Метод и маршрут | Действие |
| --- | --- |
| `GET /api/admin/users` | Получить пользователей, только поля `id`, `clientName`, `clientPhone`, `role` |
| `PATCH /api/admin/users/:id/role` | Изменить роль, тело запроса `{ "role": "admin" }` или `{ "role": "user" }` |
| `DELETE /api/admin/users/:id` | Удалить аккаунт и его refresh-токен в Redis |

Все эти маршруты проходят через `Auth` и `roleMiddleware`. Для отсутствующего аккаунта возвращается 404, для неизвестной роли — 400. В список пользователей и результат смены роли пароль не включается.

В `roleMiddleware.js` роль теперь читается из текущей записи пользователя в БД. Это требуется для смены ролей через панель. Пониженный администратор сразу теряет права, а повышенный пользователь получает их даже с ранее выданным JWT. Проверка также отклоняет удалённый аккаунт. Формат токенов сохранён.

Удаление аккаунта вызывает `user.destroy()`. Связанные записи обрабатываются существующими внешними ключами БД. Refresh-токен удаляется до удаления аккаунта, поэтому при недоступном Redis операция завершается ошибкой до изменения БД.

## Товары и услуги

Панель использует готовые контроллеры и маршруты.

| Метод и маршрут | Контроллер |
| --- | --- |
| `POST /api/product` | `postProduct`, создание товара |
| `GET /api/services?page=1&limit=10` | `getFavorsQuery`, список услуг |
| `POST /api/services` | `postFavor`, создание услуги |
| `PATCH /api/services/:id` | `patchFavor`, редактирование услуги |
| `DELETE /api/services/:id` | `deleteFavor`, удаление услуги |

В контроллере услуг `limit` и `offset` приводятся к числам перед передачей Sequelize. При редактировании проверяется количество обновлённых строк, поэтому отсутствующий ID возвращает 404.

Создание товаров, создание и редактирование услуг возвращают ошибки валидации модели как JSON с кодом 400 и полем `message`. Ограничения полей берутся из существующих моделей.

## Запуск и проверка

Установить зависимости командой `npm ci`, настроить локальный `.env` и запустить `npm run dev`. Для существующей авторизации нужны PostgreSQL, Redis и переменные `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `PORT`, `REDIS_URL`, `ACCESS_KEY`, `REFRESH_KEY`. Фронтенд запускается на `http://localhost:5173`, API — на `http://localhost:5000`.

Проверены HTTP-маршруты с настоящими middleware JWT и проверки ролей. Проверены доступ гостя и пользователя, смена ролей со старым JWT, удаление аккаунта, отсутствие паролей в списке, отсутствующие записи и валидация моделей Sequelize. В этой проверке обращения к PostgreSQL и Redis заменялись данными в памяти. Подключение к рабочей БД и её внешние ключи отдельно не проверялись.
